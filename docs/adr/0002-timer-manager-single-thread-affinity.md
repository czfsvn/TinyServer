# TimerManager 采用单线程亲和 + 入站队列

Status: accepted

`TimerManager` 的时间轮（`wheels_map_`、`timers_`、`temp_timers_`、`longtime_timers_`）此前完全没有同步保护，而驱动源 `Service::tick()` 跑在 `IOContextPool` 的定时线程上，业务侧又可能在 `asio_pool_size=2` 的工作线程里注册定时器——这是真实存在的数据竞争。我们决定：**时间轮内部只在 tick 线程上被触碰，轮子本身不加任何锁；对外接口不直接入轮，而是把定时器投进入站队列，`tick()` 开头统一收割后再入轮。**

## Considered Options

- **单线程亲和 + 入站队列（选定）**：只有入站队列需要同步（可做成双缓冲 swap 或 SPSC ring）。轮子内部彻底无锁，O(1) 特性不打折。附带收益是回调里注册定时器天然不会落进"正在遍历的槽"，因此不可能出现"新定时器被本拍执行、随后被 `timer_list.clear()` 连锅端掉"的问题。
- **全局互斥锁**：最直观，但 `std::mutex` 不可重入，必须先把槽里的链表 `swap` 出来、解锁、再执行回调，否则回调里注册定时器会自死锁；同时持锁跑回调会把主循环卡在这把锁上。50ms 的频率下锁竞争不是瓶颈，重入才是真正的坑。
- **不加锁，靠约定只在主线程注册**：零改动，但项目本身就是多线程 io_context 池，等于埋雷。

## Consequences

- 注册到生效最多延迟一拍（等于 `main_loop_interval_ms`）。这是刻意的取舍。
- 为了不额外损失精度，入站队列里存的必须是**绝对到期时刻**的定时器，收割时用收割时刻重算槽位——这样只有"生效延迟"，没有"到期误差"。
- 取消定时器也必须走同一条队列，不能直接在业务线程里改轮子状态。
